# Database Migration Validator

[![CI](https://github.com/IgnacioMendozaRojas/db-migration-validator/actions/workflows/ci.yml/badge.svg)](https://github.com/IgnacioMendozaRojas/db-migration-validator/actions/workflows/ci.yml)
![Python](https://img.shields.io/badge/python-3.11%20|%203.12%20|%203.13-blue)
![License](https://img.shields.io/badge/license-MIT-green)

Moving a database to a new server, a new engine or a new version is easy to do and hard
to *prove*. Row counts match and the cutover is declared a success; a week later someone
notices that a nightly job cannot read a table because a grant was not recreated, or that
amounts lost their decimals because a column was created with the wrong scale.

`dbmv` takes a snapshot of the database **before** and **after** and proves that nothing
was lost: structure, volumes, the content itself, and who has access to what. I built it
from the checks I needed when validating a production database migration in a bank's
risk area, where a silently changed number is worse than an outage.

```bash
dbmv snapshot "$OLD_DB_URL" -o before.json      # before cutover
dbmv snapshot "$NEW_DB_URL" -o after.json       # after cutover
dbmv compare before.json after.json -r report.md
```

`compare` exits with code 1 on any critical finding, so it can gate a cutover script or
a CI job. Snapshots are plain JSON: they can be archived as evidence for audit.

## What it checks

| Layer | Checks | Why it matters |
|---|---|---|
| **Structure** | tables, views, columns, types, nullability, primary keys, indexes, foreign keys | A missing index does not lose data but can turn a 2-second report into a 2-hour one |
| **Volume** | exact row count per table | The first thing anyone checks, and not enough on its own |
| **Content** | order-independent fingerprint per table and per column, null counts | Catches values that changed while the row count stayed the same |
| **Access** | object grants per user/role (Oracle, SQL Server, PostgreSQL, MySQL) | The data is fine but the application or the batch account can no longer read it |

Every finding is classified: **critical** (data or access lost or altered), **warning**
(structural drift such as a narrower numeric scale or a missing index) or **info**
(additions, and type renames that are equivalent across engines, such as `VARCHAR2`
to `VARCHAR`).

## Example report

A migration with four typical silent failures: three rows from a failed load batch, a
column created as `NUMERIC(14,0)` instead of `NUMERIC(14,2)`, an index not recreated and
a role that was not re-granted. Generated by [`examples/demo.py`](examples/demo.py)
against PostgreSQL. Full report: [`docs/sample_report.md`](docs/sample_report.md).

> **FAIL**: data or access differs between source and target.
>
> | Category | Object | Detail |
> |---|---|---|
> | ✗ rows | `accounts` | row count 500 -> 497 (-3) |
> | ✗ content | `accounts` | content fingerprint differs |
> | ✗ privilege | `public.accounts` | SELECT for nightly_batch lost |
> | ⚠ type | `accounts.balance` | NUMERIC(14, 2) -> NUMERIC(14, 0) |
> | ⚠ index | `accounts` | index on (customer_id) missing |

## How the content fingerprint works

Comparing data across two servers usually means exporting both and diffing files, or
writing `ORDER BY` queries that are slow and engine-specific. Instead:

1. Every value is put in a **canonical form** so engines agree on trivia: `Decimal('1.00')`
   and `1`, an Oracle `DATE` at midnight and an ANSI `DATE`, `'RETAIL    '` in a padded
   `CHAR` and `'RETAIL'`, and floating-point noise in the last digits.
2. Each row is hashed with SHA-256.
3. The table fingerprint is the **sum** of the row hashes modulo 2⁶⁴. Addition does not
   care about order, so rows can be read in whatever order each engine returns them,
   with no sorting, and duplicate rows still count (unlike XOR).
4. The same is done per column, so when a table differs the report says *which* columns.

The test suite checks that the same data fingerprints identically on **SQLite and
PostgreSQL**, and that inserting rows in reverse order does not change anything.

## Supported engines

Any SQLAlchemy dialect works for structure, counts and content. Grants are read from
Oracle (`ALL_TAB_PRIVS`), SQL Server (`sys.database_permissions`), PostgreSQL and MySQL
(`information_schema.table_privileges`).

```bash
pip install -e ".[oracle]"      # or [sqlserver], [postgres]
dbmv snapshot "oracle+oracledb://user:pw@host:1521/?service_name=PRD" --schema RISK -o before.json
```

Options: `--schema` (repeatable), `--exclude TABLE`, `--no-hash` for structure and counts
only, `--max-rows-for-hash N` to skip content hashing on very large tables, and
`--ignore-types` on `compare` for cross-engine moves. The URL can come from `DBMV_URL` so
passwords stay out of shell history.

## Development

```bash
pip install -e ".[dev,postgres]"
pytest                                   # SQLite tests
DBMV_PG_URL=postgresql+psycopg://postgres@localhost:5432/postgres pytest   # + PostgreSQL
```

CI runs the full suite on Python 3.11-3.13 against a real PostgreSQL 16 service.
